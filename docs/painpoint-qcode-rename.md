# 痛点拆解：全局重命名 zcode → qcode + 蓝紫色主题定制

> 核心痛点（一句话）：用户希望将代码中所有 `zcode` 字符串全局替换为 `qcode`，并将主题色调整为蓝紫色系，以实现品牌定制。
>
> 来源：`painpoints/pp14.md` ｜ 拆解时间：2026-09-23

## 1. 痛点分支

- 痛点 A：**名称替换不完整** — 代码中多处硬编码的 `zcode` 字符串（CLI 包名、agent 名称、tokenizer 标识符、Symbol 键等）分散在多个子包和工具目录中，全局替换极易遗漏或误替换。
- 痛点 B：**主题色缺乏明确基准** — 当前主题色未提供参考值，"蓝紫色"是无明确边界的描述词，可能导致多轮返工。
- 痛点 C：**打包命令同步更新** — `pnpm` 工作区命令、npm `name` 字段、bin 入口点需要保持一致，单独改一处会破坏构建。

## 3. 名词衍生：核心指标 & 数据结构

### 3.1 核心指标

| 指标 | 计算方式 | 业务意义 | 度量频率 |
|------|----------|----------|----------|
| **zcode 残留率** | 替换后仍包含 `zcode` 字符串的文件数 / 全局文件总数 | 名称替换完整性，理想值 = 0 | 一次性检查 |
| **色相偏离度** | 当前主色相与目标区间（260°–290°）的差值（度） | 颜色达标程度，理想值 = 0° | 一次性检查 |
| **打包成功率** | `pnpm build` 退出码 = 0 的比例 | 构建链路完整性，理想值 = 100% | 每次 CI |
| **CLI 启动成功率** | `qcode --version` 正常输出版本号的比例 | bin 入口正确性，理想值 = 100% | 每次构建后验证 |

### 3.2 数据结构

```yaml

  primaryColor: string      # 当前色值未知，需调整为 HSL(260-290, X%, Y%)
  hue: number              # 色相（度）

  lightness: number         # 亮度（%）
```

## 4. 动词衍生：业务流程

### 4.1 主流程

```mermaid
flowchart LR
  A[执行全局替换脚本] --> B[更新 package.json name 字段]
  B --> C[验证 bin 入口]
  C --> D[运行 pnpm build]
  D --> E[执行 qcode --version]
  E --> F[调整主题色为蓝紫色]
  F --> G[视觉验收]
```

### 4.2 异常流程

| 触发点 | 失败场景 | 系统响应 |
|--------|----------|----------|
| 全局替换 | 某些文件被遗漏（Symbol 键、tokenizer 字符串等深层次引用） | 打包成功但运行时 `Symbol.for("zcode.xxx")` 不匹配，CLI 行为异常 |
| package.json 更新 | npm 包名含大写或特殊字符导致发布失败 | pnpm 工作区解析失败 |
| bin 入口 | bin 键名未同步更新，`command not found` | CLI 无法通过命令行唤起 |
| 颜色调整 | 蓝紫色过于接近紫色导致可读性差（对比度不足） | 需要调整饱和度/亮度而非仅色相 |

### 4.3 决策分支

- `if 色相差 > 30°` → 继续微调色相
- `if 替换遗漏（残留率 > 0）` → 重新运行精确匹配替换

## 5. 形容词 / 副词衍生：潜在需求

### 5.1 隐含约束

- "全局"替换必须使用**精确匹配**（word boundary），避免误替换如 `ozcode` → `oqcode`
- `Symbol.for("zcode.xxx")` 中的字符串**必须**随名称一起改，否则 `Symbol.for()` 返回不同引用，导致事件总线断裂
- `tokenizer: "zcode.estimateTokens.v1"` 标识符若不改，token 计算功能可能调用错误端点

### 5.2 边界场景

- **目录名包含 `zcode`**：当前 `apps/qcode-cli` 目录是否也改？（影响 import path 和 CI 配置）
- **npm scope**：`@zcode/` 下的 scope 包是否也改？
- **node_modules 缓存**：首次替换后需清除缓存再构建
- **历史 git 记录**：已有提交中的 `zcode` 字符串不会被自动清理

### 5.3 非功能性需求

- **性能**：全局替换操作本身无性能要求（N/A）
- **可用性**：替换后 CLI 启动成功、TUI 可用
- **安全 / 合规**：Symbol 键改动后，所有依赖该 Symbol 的通信方需要同步更新；跨进程通信（stdio 协议）不受影响
- **可观测**：构建产物中不存在残留 `zcode` 字符串

## 7. MVP 启动路径

### Phase 1: MVP（建议 1–2 天）

- **目标**：完成核心的名称替换，打包可成功，CLI 可启动
- **包含功能**：F-001（全局名称替换）、F-002（package.json 更新）、F-003（CLI 启动验证）
- **理由**：三者顺序依赖；F-001 是基础，F-002 改包名，F-003 验证结果；均为 P0，缺一则 CLI 无法正常工作
- **验证指标**：zcode 残留率 = 0%，打包成功率 = 100%，CLI 启动成功率 = 100%
- **退出条件**：构建产物中零 `zcode` 残留，`qcode --version` 正常输出

### Phase 2: 增强（建议 0.5–1 天）

- **目标**：完善收尾检查，防止未来引入新残留
- **包含功能**：F-005（构建后残留检查）
- **理由**：P1，手动检查容易被遗忘，需要自动化卡点
- **验证指标**：CI 每次构建均执行残留检查，残留率始终 = 0
- **退出条件**：连续 3 次 CI 构建无残留

### Phase 3: 完善（建议 1 天）

- **目标**：调整主题色为蓝紫色系
- **包含功能**：F-004（主题色蓝紫色调整）
- **理由**：P1，视觉定制不影响核心功能，放在最后
- **验证指标**：色相偏离度 = 0°
- **退出条件**：TUI 视觉验收通过，对比度满足 WCAG AA

## 9. 待澄清

以下问题需要在实施前确认，否则可能导致返工：

1. **目录名是否改？** `apps/qcode-cli/` 目录是否也改名为 `apps/qcode-cli/？如改，CI 配置（turbo.json、github workflows）中的路径引用均需同步更新。
2. **npm scope 是否改？** 当前 `@zcode/*` 下的 scope 包（`@zcode/cli`、`@zcode/core` 等）是否也改为 `@qcode/*`？还是仅改产品名，scope 保留？
3. **已有历史提交中的 zcode 是否清理？** git 历史中的 `zcode` 字符串不会被自动清理，清理历史需要 `git filter-branch` 或 `git replace`，成本较高，是否必要？
4. **蓝紫色的具体色值？** "蓝紫色"（HSL 260°–290°）跨度 30°，建议提供具体参考色（如 `#7C3AED` 紫色或 `#2563EB` 蓝色），否则 F-004 需要多轮视觉评审。
5. **AGENTS.md 和 CLAUDE.md 中的 zcode 引用是否改？** 这两个文件属于项目规范文档，其中的 `zcode` 字符串（如"zcode CLI"、"zcode TUI"）是否属于"全局相关"的替换范围？
