# 痛点拆解：把仓库做成不依赖公网的独立个体

> 核心痛点（一句话）：**要把 zcode 交付到拿不到公网的环境的维护者**，在 **从 `make install` 到构建、再到启动 zcode 的全链路上**，因为 **远程资源的获取点分散在多个脚本里各自直连外网，且下载落点落在被 `make clean` 删除、被 `.gitignore` 忽略的目录里**，导致 **交付物既装不起来也跑不完整，而且没有任何一份台账能回答"这个仓库到底依赖多少外部资源、有没有被篡改、有没有后门"**。
>
> 来源：`painpoints/pp2.md` ｜ 拆解时间：2026-09-22
>
> 已确认前提：**npm 包是唯一被豁免的远程源**（原话"除了 npm 包之外"）｜范围：**构建期 + 运行期都要**（"相对独立的个体"不是"构建能过"）｜扫描范围：**整体**（原话"整体扫一遍"）
>
> ⚠️ **判据订正（2026-09-22，本文后于落地执行）**：实施过程中用户澄清了资源范围的判据——**智谱自家的远程资源在本地留一份；第三方通用包直接下载即可、不保留**。本文 §3 起以"资源"泛称，未区分归属方，导致初版实现范围偏大：曾把 Node 运行时（336 MiB）与 8 个上游源码包（~25 MiB）纳入本地化，它们实为第三方通用包。按订正后的判据，**真正的目标是智谱自家 CDN 上的官方插件市场——清单 + 26 个插件包 + 26 个图标，10.8 MiB**；本文 §4 的 F-006「本地化插件市场」因此**不是 Phase 2 的增强项，而是本次的核心交付**。字段结构（§3.2 的 `RemoteResource`）不受影响，仅新增 `vendor` 与 `vendoring` 两个字段表达归属与取舍。详见 `plan-offline-vendoring.md` 的判据订正记录。

## 1. 痛点分支

- 痛点 A：**获取点分散、各自直连公网**。至少四类，分属不同脚本、**没有统一入口、没有统一台账**：① `nodejs.org/dist/v<ver>/` 的 SEA 基座 Node 运行时（`apps/qcode-cli/packages/cli/scripts/sea-node-download.mjs:90,121`，带 SHASUMS256 校验，且有 `--node-binary` 这条离线逃生口）；② `codeload.github.com` 与 `sourceware.org` 的**上游源码包**（bfs / ugrep / oniguruma / pcre2 / zlib / bzip2 / zstd / brotli，`scripts/native-search-tools-config.mjs:47-90`）；③ `cdn-zcode.z.ai` 的官方插件市场清单与资产；④ `api.github.com` / `github.com` 的插件安装链路。
- 痛点 B：**同一件事在仓库里有一半已经做对了，另一半没有——而"做对了的那一半"正好证明了另一半为什么是痛点**。做对的是 `apps/qcode-cli/dependencies/native-search/`：19 个预编译压缩包已入库、附 `SHA256SUMS`、`prepare-native-search-tools.mjs:44` 逐个校验后才解包，**全程不联网**，并且它既不在 `.gitignore` 里、也不会被 `make clean` 删——这正是诉求想要的标准形态。没做对的是**同一条链路的源码构建路径**（`pnpm build:native-search`，走 `native-search-tools-process.mjs:65` 的 `curl -L`），它是**唯一一个硬依赖公网、且没有任何离线退路的构建步骤**。此外 `bundled-resources/`、`prebuilds/`、`mock-cdn/`、`/.tmp/` 都在 `.gitignore` 里，`make clean`（`scripts/clean.mjs`）按名字删 `node_modules/` 与 `dist/` ——资源**既进不了仓库，也活不过一次清理**。
- 痛点 C：**运行期的 CDN 依赖只解决了一半，缺的那一半恰好没有退路**。官方插件市场的**清单**有本地内置分片兜底：`official-marketplace.ts` 把 `bundled-marketplace.json` 与 `cdn-marketplace.json` 分片持久化后合并，CDN 拉取失败或从未拉取过也不影响内置插件可列出（拉取本身是惰性的：无本地清单或用户显式刷新时才发生）。但**插件图标指向 `https://cdn-zcode.z.ai/zcode/official-plugin/assets`（`official-plugin-definitions.ts:58`）是直接渲染的 CDN URL，没有任何本地兜底**；而通过 GitHub 安装第三方插件的 `github-archive-source.ts:79`（`api.github.com/.../zipball/...`）**没有 sha256 校验**——与之相对，`type: zip` 那条路径是校验了 64 位 sha256 才解包的。同一个产品里，两条同样从公网拿代码的路径，一条校验一条不校验。
- 痛点 D：**"离线"目前是一条没有接线的设计，而不是一个能跑的能力**。`INTRANET_MACHINE_HOST` / `ZCODE_DEPS_BASE_URL` / 内网探针（`scripts/intranetDefaults.mjs`、`packages/shared/src/intranetDefaults.ts`）定义了地址与"未配置就报错"的提示，但**下载侧没有任何代码消费它**，只有 `upload-sea-smb.mjs` 把它当上传目标用。也就是说：今天既不能靠公网（要被去掉），也不能靠内网镜像（没接线），本地化是唯一可行的方向。
- 痛点 E：**资源没有统一台账，无法审计**。资源信息散落在 `third-party/runtime/sources.json`、`third-party/native-search/sources.json`、`scripts/native-search-tools-config.mjs`、`scripts/remote-native-search-tools-config.mjs`、`sea-targets.mjs` 里，**格式各异**（有的带 sha256 与 url，有的只有 sha256 没有下载地址，有的只有 url）。因此回答不了"全量是多少"，也就无法证明"所有"。
- 痛点 F：**仓库里已有绕过既有规则的残留**（即用户要扫的"特例判断"的现成样本）。`.env.bak-before-vendor-migration` **被 Git 跟踪**且含一个 `BIGMODEL_API_KEY`——它绕开了 `.gitignore` 的 `.env` 规则（后缀 `.bak-before-vendor-migration` 不匹配 `.env`）；`.gitignore` 中多条规则引用的脚本（`scripts/ci/ci-repo-hygiene.mjs`、`scripts/cua-helper-sea-base.mjs`）**已不存在**；`scripts/prepare-prebuilds.sh` 更彻底——它 `exec node scripts/prepare-prebuilds.mjs`，而那个 `.mjs` **不在仓库里**，这个入口**无条件失败**。
- 痛点 G（正面基线，须保留）：**仓库里已经有三处"本地优先 + 远端可选"的正确形态**，本地化不该另起一套，而应把它们抽象成通用能力：① `dependencies/native-search/` 的预编译包（入库 + 校验 + 联网为零）；② 插件市场的内置分片（远端失败也能列出内置插件）；③ 内置 Provider 配置 `config/provider/zcode-builtin.json`（构建期烘焙，`zcode-builtin-download.ts:38` 从 `<endpointOrigin>/api/v1/client/configs` 拉到的远端版本被明确定义为**可丢弃的缓存**，且远端配置只带 revision 单调校验、不带 checksum）。

## 2. 词性拆解

### 2.1 名词（Entities）

| 实体       | 含义                                                      | 角色 | 状态                     |
| ---------- | --------------------------------------------------------- | ---- | ------------------------ |
| 远程资源   | 需要从公网获取的二进制 / 源码包 / 清单 / 许可原文         | 客体 | 持久（核心）             |
| 资源台账   | "有哪些资源、从哪来、sha256 是多少、落在哪"的机器可读清单 | 客体 | 持久（核心）             |
| 本地副本   | 随仓库入库的那一份资源                                    | 客体 | 持久（核心）             |
| 下载缓存   | 下载中途 / 可重建的临时落盘                               | 客体 | **临时**（需 TTL 与 GC） |
| 校验和     | sha256，判定完整性、证明资源未被篡改                      | 客体 | 持久（核心）             |
| 受保护目录 | 不被 `make clean` 删除、不被 `.gitignore` 命中的落点      | 客体 | 持久（核心）             |
| 使用者     | 交付者（入库方）+ 安装者（断网侧）                        | 主体 | 持久（核心）             |

> 核心实体保留 7 个。以下为**关键外围实体**，不参与核心指标与表结构，但决定边界：

| 实体         | 含义                                                                                   | 角色 | 状态                                       |
| ------------ | -------------------------------------------------------------------------------------- | ---- | ------------------------------------------ |
| 内置基线     | 构建期就烘焙进包的本地默认值（已入库的预编译包、插件市场内置分片、内置 Provider 配置） | 客体 | 持久（**既有正确形态，是本方案的参照系**） |
| 官方插件市场 | 运行期从 CDN 拉取的 marketplace 清单与插件资产                                         | 客体 | 持久（**运行期**）                         |
| 内网镜像     | `INTRANET_MACHINE_HOST` 指向的 HTTP 服务                                               | 客体 | 持久（**定义了但下载侧未接线**）           |
| 扫描报告     | 一次"后门 + 特例判断"的产出                                                            | 客体 | **临时**（一次交付一份，不落仓库）         |

### 2.2 动词（Actions）

| 动作             | 触发     | 终结状态                                                   | 时序                     |
| ---------------- | -------- | ---------------------------------------------------------- | ------------------------ |
| 枚举远程资源     | 系统被动 | 得到全量台账（id + url + sha256 + 用途 + 目标平台 + 体积） | #1                       |
| 下载资源         | 系统被动 | 资源字节落到本地                                           | #2                       |
| 校验资源         | 系统被动 | 判定 通过 / 不通过                                         | #3                       |
| 落盘到受保护目录 | 系统被动 | 资源位于 clean 与 ignore 都不触及的位置                    | #4                       |
| 入库             | 用户主动 | 资源进入 Git 索引，克隆即得                                | #5                       |
| 安装 / 构建      | 用户主动 | 命中本地副本即止；本地缺失才考虑回源                       | #6                       |
| 启动 zcode       | 用户主动 | 断网也能列出官方插件与资产                                 | #7                       |
| 清理工作区       | 用户主动 | 可重建产物被删，本地副本**保留**                           | #8                       |
| 扫描资源         | 用户主动 | 得到"后门 + 特例判断"报告                                  | #9                       |
| 刷新本地副本     | 用户主动 | 台账与副本更新到新版本                                     | 旁路（正向，但必须显式） |

### 2.3 形容词 / 副词（Rules）

| 限定词                             | 含义                                           | 限定对象                   |
| ---------------------------------- | ---------------------------------------------- | -------------------------- |
| **所有**                           | 覆盖必须是全集；"挑几个常用的"不成立           | 资源范围（**最关键规则**） |
| **除了 npm 包之外**                | npm 注册表是唯一被豁免的远程源                 | 资源范围（豁免边界）       |
| 不要**依赖**远程资源               | 判据是"能不能不依赖"，不是"能不能访问到"       | 构建 / 运行链路            |
| 在 make 指令清理的时候**不做清理** | 资源必须活过一次 `make clean`                  | 清理动作                   |
| **随仓库上传**                     | 资源进 Git 索引，克隆即得                      | 本地副本                   |
| **不在 git ignore 里**             | 落点不能落在任何忽略规则的覆盖下               | 受保护目录                 |
| **相对独立的个体**                 | 可整体拷贝、断网可用                           | 交付形态                   |
| **整体**扫一遍                     | 扫描范围 = 本次本地化的全部资源                | 扫描动作                   |
| **后门**                           | 隐蔽的、超出声明用途的行为                     | 扫描目标                   |
| **特例判断**                       | 绕过通用逻辑的分支、硬编码白名单、旁路 if-else | 扫描目标                   |
| 内网 / 离线（隐含场景）            | 拿不到公网，也不一定有内网镜像                 | 交付场景                   |
| 下载**完之后**                     | 扫描是后置环节，依赖本地化完成                 | 时序                       |

> 2.3 是本次的关键：**"所有"** 与 **"不在 git ignore 里"** 决定了这件事不能靠"记住别再写进忽略名单"，而必须落成**可复核的断言**——因为仓库现状里已经有反例（`bundled-resources/` 正是被忽略的）。

## 3. 名词衍生：核心指标 & 数据结构

### 3.1 核心指标

| 指标             | 计算方式                                        | 业务意义（反向测试）                                                                  | 度量频率          |
| ---------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------- |
| 远程资源总数     | 台账条目数                                      | "到底依赖多少外部资源"的分母。若从 10 涨到 40，负责人会立刻问"这些新的是什么、谁加的" | 每次台账变更      |
| 本地化覆盖率     | 已入库资源数 / 台账总数                         | 核心指标，必须 100%（npm 除外）。若降到 90%，断网构建会**随机**失败且失败点不可预测   | 每次构建          |
| 断网构建成功率   | 屏蔽全部非 npm 出网后 `make install` 成功的比例 | "相对独立的个体"的直接验收。非 100% 即结论不成立                                      | 每次交付          |
| 断网运行可用度   | 断网启动后官方插件市场可列出的插件数 / 应有数   | 痛点 C 的量化。若降到 0，用户看到的是"装好了但什么都没有"，且没有报错                 | 每次交付          |
| 清理后资源存活率 | `make clean` 后本地副本仍存在数 / 台账总数      | 痛点 B 的量化，必须 100%。低于 100% 意味着下一次构建又要回公网                        | 每次 `make clean` |
| 忽略命中数       | `git check-ignore` 命中的本地副本路径数         | "不在 git ignore 里"的量化，必须**恒为 0**                                            | 每次入库          |
| 未校验资源数     | 台账中缺 sha256、或校验未实际执行的条目数       | 审计底线，必须恒为 0。不为 0 时"扫过一遍"没有任何意义                                 | 每次下载          |
| 仓库体积增量     | 本轮入库资源占用的字节数                        | 现实约束。若从 50MB 涨到 500MB，负责人会叫停——克隆成本与 CI 拉取时间会成为新的痛点    | 每次入库          |
| 扫描覆盖率       | 已扫描资源数 / 台账总数                         | "整体扫一遍"的量化，必须 100%                                                         | 每次交付          |
| 高危发现数       | 扫描出后门 / 隐蔽行为 / 特例判断的条目数        | 交付放行依据                                                                          | 每次交付          |

### 3.2 数据结构

```yaml
# 资源台账：一条 = 一个需要本地化的远程资源；这是唯一真源，脚本不得再内联 URL
RemoteResource:
  id: string                  # 稳定标识，如 "node-runtime-24.14.0-darwin-arm64"
  kind: enum[                 # 类别决定它落哪条链路（构建期 / 运行期）
    runtime,                  # Node 运行时（SEA 基座）
    prebuild,                 # 预编译二进制（bfs / ugrep / ripgrep / zstd / brotli）
    source-tarball,           # 从源码构建用的上游压缩包
    marketplace-manifest,     # 官方插件市场清单
    plugin-asset,             # 插件图标等资产
    license-text              # 许可原文（已本地化，作为既有范例）
  ]
  url: string                 # 公网来源；仅供溯源，不参与构建
  sha256: string              # 校验和；缺失即视为"未本地化"
  vendored_path: string       # 仓库内相对路径（消费方唯一允许读取的位置）
  scope: enum[build, runtime] # 决定它只需活过 make clean，还是运行期也必须可读
  platforms: [string]         # 缺失的平台就是断网构建的失败点
  size_bytes: number          # 体积预算的输入
  consumers: [string]         # 消费它的脚本或运行时代码位置

# 受保护目录：本地副本唯一允许落地的地方
ProtectedRoot:
  root: string                # 如 third-party/ 或新增的 vendored/
  clean_policy: keep          # 显式 keep，而非靠目录名恰好躲开 clean
  ignore_policy: tracked      # 显式 tracked，而非靠"恰好没写进 .gitignore"
  size_budget_bytes: number   # 超出即需显式决策（见 §4.2 体积超限一行）

# 扫描报告：一次"后门 + 特例判断"的产出（临时实体，不落仓库）
ResourceScanReport:
  generated_at: timestamp
  covered: [ref(RemoteResource)]
  findings:
    - resource: ref(RemoteResource)
      kind: enum[backdoor, special-case, stale-reference, secret-exposure]
      evidence: string        # 文件 + 行号 + 原文片段
      severity: enum[high, medium, low]
```

> **临时实体的含义**：`下载缓存` 与 `ResourceScanReport` 都不进仓库 → 前者需要 TTL / GC 逻辑，后者每次交付重新生成即可，不做增量维护。

## 4. 动词衍生：业务流程

### 4.1 主流程

```mermaid
flowchart LR
  A[枚举远程资源] --> B[下载] --> C[校验 sha256] --> D[落盘到受保护目录]
  D --> E[入库 · 随仓库上传]
  E --> F[构建/安装 · 命中本地副本]
  F --> G[启动 zcode · 断网可列插件]
  G --> H[扫描 · 后门 + 特例判断]
  I[make clean] -.->|只删可重建产物| D
```

### 4.2 异常流程

| 触发点 | 失败场景                       | 系统响应                                                                             |
| ------ | ------------------------------ | ------------------------------------------------------------------------------------ |
| 枚举   | 漏掉某处硬编码 URL，台账不全   | 对全仓做一次独立 URL / registry 引用扫描，与台账取差集；差集非空即失败，并打印缺失项 |
| 下载   | 公网不可达 / 超时              | 立即失败并指名 `资源 id + url`；**不回退**到"用上次的残留文件"静默降级               |
| 校验   | sha256 不匹配                  | 拒绝落盘并删除半成品，同时报出期望值 / 实际值                                        |
| 落盘   | 落入被 `.gitignore` 命中的路径 | 入库前用 `git check-ignore` 断言；命中即失败，不靠人工复核                           |
| 落盘   | 落入 `make clean` 的删除范围   | 断言路径在 `ProtectedRoot.clean_policy = keep` 白名单内；"恰好没被删到"不算通过      |
| 入库   | 仓库体积超预算                 | 报告增量与最大贡献者，交由用户显式决定"入库还是改走镜像"，不静默入库                 |
| 构建   | 本地副本缺当前平台             | 指名缺失的 `platform`，不静默回源补齐                                                |
| 构建   | 本地副本存在但与台账版本不符   | 以台账为准判定，不做"看起来是那个文件"的猜测                                         |
| 运行   | 插件市场本地副本缺失 / 损坏    | 市场降级为空但**不阻塞启动**；明确告知"本地目录缺失"，而不是给一个无声的空列表       |
| 清理   | `make clean` 误删本地副本      | 清理后自检：台账逐条断言存在，缺任何一条即失败                                       |
| 扫描   | 扫描未覆盖全部台账             | 报告标出未覆盖项；覆盖不全**不得**出"通过"结论                                       |
| 扫描   | 资源体积过大导致扫描超时       | 分片扫描并保留进度；不以超时冒充"无发现"                                             |

### 4.3 决策分支

- `if 资源 kind == runtime` → 按 平台 × 版本 逐条本地化；缺失平台显式失败，不跳过
- `if 资源 scope == runtime` → 落点必须运行期可读，不能只在构建期存在
- `if 本地副本存在 且 sha256 匹配` → 直接使用，**不发任何网络请求**
- `if 本地副本缺失` → 失败并指名（默认）；仅当用户显式发起刷新时才回源
- `if git check-ignore 命中本地副本路径` → 入库前失败
- `if make clean 的目标在 ProtectedRoot 之下` → 跳过删除并记录
- `if 扫描发现 severity == high` → 阻断交付，逐条给出证据
- `if 资源属于 npm 包` → 落在豁免边界内，记入台账但标记为"豁免"，不做本地化

## 5. 形容词 / 副词衍生：潜在需求

### 5.1 隐含约束

- **"所有"** → 需要一个**可复核的枚举口径**：对全仓扫描 URL / registry 引用，与台账做差集，差集为 0 才算数。否则"所有"永远无法证明，只会不断被发现"还有漏的"。
- **"不做清理"** → `make clean` 需要一份**显式保留白名单**。靠目录命名恰好不在删除列表里是脆弱的——`scripts/clean.mjs` 目前只按 `node_modules` / `dist` 两个名字匹配。
- **"不在 git ignore 里"** → 需要一条**断言**（`git check-ignore`），而不是"记得别再写进去"。仓库里同时有正反两个例子：反例是 `bundled-resources/` 正被忽略，而它看起来恰好是放这类资源的地方；正例是 `apps/qcode-cli/dependencies/native-search/` 的 19 个预编译包——它们既被跟踪、也不会被 `make clean` 删，**已经满足这条规则**。所以这不是"做不到"，而是"没有统一做法"。
- **"随仓库上传"** → 需要一个**体积预算**。6 个 SEA target 的 Node 运行时是数十 MB 级 × 6，仓库会从 `.git` 37MB 的量级跳到数百 MB；克隆时间与 CI 拉取成本是新的真实代价，不能等到入库那天才发现。
- **"相对独立的个体"** → 需要**可验证的离线态**：断网跑通一次才算成立，不能靠"代码里没有明显的 fetch"推定。`mise` 与 `pnpm` 自身的工具链下载也要算进来。
- **"下载完之后整体扫一遍"** → 扫描需要**基线**：是"本次新增的本地副本"，还是"整个仓库"？范围不同，"特例判断"的结论完全不同（仓库里已经有真实特例：`.env.bak-*`、`.gitignore` 中引用已删脚本的规则、`patches/` 对 `@ai-sdk/*` 的改写）。
- **"后门"** → 需要**可复现的证据**（文件 + 行号 + 片段），而不是"看起来没问题"的结论。
- **"特例判断"** → 这一条恰好命中仓库现状：`patches/@ai-sdk__anthropic@3.0.81.patch` 往 Anthropic 协议里加了一个 `video/*` content block，是**有意为之的特例**且带注释说明；而 `.gitignore` 里引用已不存在脚本的规则是**无意的残留特例**。扫描必须把两者分开。
- **npm 豁免（隐含）** → 需要在台账里**显式记录豁免边界**，否则下一个维护者会把 npm 包也当资源去本地化。

### 5.2 边界场景

- **平台边界**：6 个 SEA target（darwin / linux / win × arm64 / x64，见 `sea-targets.mjs`）。只装宿主平台的开发者与"全平台交付"的诉求不一致，需要明确交付目标平台集合。
- **版本边界**：`mise.toml` pin 的 Node 是 24.14.0，而 `third-party/runtime/sources.json` 里同时留着 22.16.0 与 24.14.0 两份许可原文——本地化要覆盖到实际被使用的那一版，不能按"目录里有什么"推定。
- **体积边界**：单文件一旦超过托管方的硬限制（如 GitHub 100MB），"随仓库上传"直接不可行，必须在动手前算出来。
- **网络边界**：完全断网 / 只有内网镜像 / 只有 npm 私服——三种可达性组合下行为不同，验收要覆盖至少前两种。注意内网镜像**当前没有下载侧消费者**，所以"只有内网镜像"这一格今天等价于断网。
- **校验边界**：同一产品内两条从公网取代码的路径标准不一致——`type: zip` 的插件包校验 64 位 sha256 后才解包，而 GitHub zipball 路径（`github-archive-source.ts:79`）不校验。本地化时若把这两条都收进台账，"每条都有 sha256"这条底线就会立刻暴露出这条不一致。
- **时间边界**：资源一旦入库就不再自动更新，必须有明确的负责人与刷新动作，否则半年后会静默过期。
- **既有残留边界**：`.env.bak-before-vendor-migration` 既不在 `.gitignore` 覆盖下，又会被"随仓库上传"原样带走。

### 5.3 非功能性需求

- **性能**：下载与校验要可增量——已存在且 sha256 匹配即跳过，避免每次安装重算全部哈希。
- **可用性**：本地副本缺失时的失败必须**指名到资源 id**，而不是笼统的"下载失败"；插件市场缺失不得阻塞 TUI 启动。
- **安全 / 合规**：台账每一条必须有 sha256 且校验通过；入库前对凭据做一次扫描（`.env.bak-before-vendor-migration` 已证明这个风险是真实的）。许可原文的本地化已有既定形态（`third-party/upstream/*.txt` + `sources.json`），新资源必须并入同一套，不能另起一套。
- **可观测**：`doctor` 应能报出"本地化覆盖率 / 未校验数 / 忽略命中数 / 各平台缺失项"，让离线可用性可自查，而不是等构建失败才发现。

## 7. MVP 启动路径

### Phase 1: MVP（建议 3-5 周）

- **目标**：在断网环境下从零 `make install` 到启动 zcode，且交付物能自我说明"依赖了什么、扫过什么"
- **包含功能**：F-001, F-002, F-003, F-004, F-005
- **理由**：全部 P0，且 F-001 → F-002 → F-003 是严格依赖链；F-004 是"独立个体"唯一的证明方式；F-005 是用户明确点名的验收动作，必须在首次交付前完成，不能留到下一期
- **验证指标**：本地化覆盖率 100%（npm 除外）、断网构建成功率 100%、清理后资源存活率 100%、忽略命中数 0、扫描覆盖率 100%
- **退出条件**：完全断网下**连续两次**从零 `make install` 成功；`make clean` 后台账逐条仍存在；扫描报告不存在未处置的 `high` 发现

### Phase 2: 增强（建议 +2 周）

- **目标**：让"独立个体"在装完之后继续成立——运行期也不再回源
- **包含功能**：F-006
- **理由**：依赖 Phase 1 的台账与受保护目录；把 CDN 从"必需品"降级为"可选的增量来源"，是痛点 C 的直接解
- **验证指标**：断网运行可用度 = 应有插件数
- **退出条件**：断网启动后官方插件市场可列出**全部**应有插件；连续两周无隐式回源行为

### Phase 3: 完善（建议 +2 周）

- **目标**：让本地副本可维护，不会静默过期
- **包含功能**：F-007
- **理由**：只有等资源真的陈旧的时刻（第一次需要刷新）到来，刷新入口才具备可验证的验收场景；提前做会变成没人用的空壳
- **验证指标**：远程资源总数、仓库体积增量
- **退出条件**：完成一次真实的端到端刷新（台账 + 副本 + 入库 + 复验），且体积增量在预算内

> **工期只是参考**：决定"进入下一阶段"的是 **P0 是否全部完成 + 验证指标是否达标**，不是日历。

### 优先级说明（回应"P0 理想 ≤ 5"）

- **为什么 P0 是 5 个**：F-001 ~ F-005 构成"枚举 → 本地化 → 本地优先 → 验收 → 扫描"的完整闭环，缺任何一环都无法回答"这个仓库是不是独立个体"这个问题本身——F-001 缺失则"所有"不可证，F-003 缺失则本地化不产生任何效果，F-004 缺失则结论只是推断。F-005 是用户原话中明确点名的动作（"下载完之后整体扫一遍"），属于验收项而非增强项。
- **为什么 F-006 是 P1 而不是 P0**：它的清单部分**已经具备内置兜底**（`bundled-marketplace.json` 分片），断网不会得到空市场——所以痛点 C 并非"完全没解"，而是"缺图标兜底 + 缺安装链路校验"。真正无解的是**任意第三方插件的安装**（仓库在用户手里，不可能预置），这一条无法靠本地化解决，只能靠"内置分片可用 + 明确告知"降级。因此它更适合放在运行期闭环的 Phase 2，而不是挤压 MVP。
- **为什么 F-007 是 P1**：资源一旦入库就不再有隐式更新，刷新入口只有在第一次真实刷新需求出现时才具备验收场景；提前实现无法验证。
